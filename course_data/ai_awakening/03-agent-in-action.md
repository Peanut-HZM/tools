## 从"改一个 bug"开始

这是实战篇第一章，选最成熟的软件开发场景。先看一个真实感十足的对比——同样是"修复登录接口超时"这个 bug：

**传统方式（约 2 小时）：**
```
1. 复现问题：本地起服务，模拟超时（30 分钟）
2. 定位问题：看日志、加断点、排查是数据库慢查询（40 分钟）
3. 修改代码：加索引 + 改查询（20 分钟）
4. 验证：重新测试（20 分钟）
5. 提交：写提交信息、通知团队（10 分钟）
```

**智能体方式（约 10 分钟，人工 3 分钟）：**
```
你：修复登录接口超时的问题。线索：数据库日志里出现过慢查询警告。
    验收标准：登录接口 P99 延迟降到 500ms 以内，全部测试通过。

智能体：读取数据库日志 → 定位到 orders 表全表扫描 → 加索引并优化
        查询 → 跑测试（2 次失败，自动修复 mock 后通过）→ 压测验证
        P99 = 320ms → 提交代码 + 变更说明

你：审查 diff → 确认无误 → 合并
```

注意分工：**智能体干了体力活，人干了判断活**。

### 五大应用场景对比

| 场景 | 传统方式 | 智能体方式 | 省下的不只是时间 |
|------|---------|-----------|----------------|
| Bug 修复 | 手动定位+修改+测试 | 描述问题 → 自动修复+验证 | 定位经验被沉淀 |
| 代码审查 | 逐行阅读+写评论 | 自动扫描 + 生成建议 + 一键修复 | 审查标准更稳定 |
| 重构 | 手动分析+逐步修改 | 指定目标 → 自动重构+测试 | 不再畏惧大重构 |
| 文档生成 | 手动编写 | 分析代码 → 自动生成文档 | 文档与代码不再脱节 |
| 测试编写 | 手动设计用例 | 分析功能 → 自动生成测试 | 边界情况覆盖更全 |

### 实战演示：让智能体重构一个模块

**任务描述（注意四要素齐全）：**

```
目标：将 src/services/payment.js 从回调风格重构为 async/await 风格
约束：
- 不改变任何对外接口的签名与行为
- 不引入新的第三方依赖
- 保持现有的错误处理语义（错误码不变）
上下文：
- 该模块被 src/api/*.js 中 12 个文件调用
- 项目测试命令：npm test（现有 47 个测试全部通过）
验收标准：
- npm test 全部通过
- 接口签名 diff 为零
- 重构后的代码符合项目 ESLint 规则
```

**智能体执行过程（值得逐帧观察）：**

```
① 先跑一遍现有测试，确认起点是绿的（聪明的第一步！）
② 用 grep 找出 payment.js 的所有导出函数与调用方
③ 逐函数重构：callback → promise → async/await
④ 每重构完一个函数跑一次相关测试（小步验证）
⑤ 全部完成后跑全量测试 + ESLint
⑥ 输出报告：修改了 3 个文件、148 行；测试 47/47 通过；
   附上前后对照的关键 diff；标注了一处"疑似死代码"建议人工确认
```

三个值得学习的细节：**先确认起点是绿的**（不然分不清是谁改坏的）、**小步验证**（不等全部改完才测试）、**主动上报存疑点**（不擅自删"疑似死代码"）。

### 新手最容易踩的三个坑

1. **任务描述只给目标不给验收标准** → 智能体"改完了"但你没法快速确认改对了。验收标准是对自己的保护
2. **不加约束就放权** → 没写"不引入新依赖"，它可能顺手给你装了三个库。**你没说的，就是它自由发挥的空间**
3. **不看 diff 直接合并** → 智能体代码质量≠总是正确。审查 diff 的 3 分钟永远值得花

### 效率的真相：省下的时间去哪了？

实战数据的一个典型分布：重复劳动（查日志、跑测试、写模板代码）时间下降 60%+，但**人的时间转移到了更贵的地方**——定义清晰的验收标准、审查关键 diff、做架构决策。这不是"失业"，是**升级**：从码农升级为审核者与决策者。

### 本章小结

- 好的任务描述 = 目标 + 约束 + 上下文 + 验收标准，缺一不可
- 观察智能体工作流的三种学习信号：先验证起点、小步验证、主动上报存疑
- 三个高频坑：没有验收标准、不加约束放权、不看 diff 直接合并
- 智能体接管重复劳动，人类升职为"定义问题与把关质量"的角色

## 从"问数据"到"信数据"

"分析上季度的销售数据，找出增长最快的品类"——放在 2020 年，这是一份数据分析师一天的工作；放在今天，智能体十分钟能给你一份带图表的报告。但数据分析场景有个特殊挑战：**AI 会编数据**。这一章讲怎么用智能体做分析，以及怎么保证数字是真的。

### 完整流程：五步生成一份可信报告

```
用户："分析上季度的销售数据，找出增长最快的品类"

智能体执行：
  1. 连接数据库，先看表结构与字段含义（不瞎猜字段名！）
  2. 查询销售数据（只读账号），核对数据时间范围
  3. 按品类分组，计算环比/同比增长率
  4. 生成可视化图表
  5. 撰写分析报告，每个数字标注来源 SQL
```

注意第一步的细节：**它先看表结构再写查询**。新手直接让 AI"查一下销售额"，它只能猜你的表叫 sales 还是 orders、字段叫 amount 还是 total_price——猜错了轻则报错，重则**安静地查出一个错误的数字**。

### 防"编数据"三板斧

数据分析智能体的第一原则：**宁可说查不到，不许编数字**。

**① 只读权限 + 白名单表**

给智能体的数据库账号必须是只读的，且只能访问分析相关的表。这样它就算"想"删库也做不到，想看工资表也看不了。

**② 强制给出来源**

在提示词里立规矩：

```
规则：
1. 每个引用的数字必须注明来源 SQL 与执行结果
2. 如果查询结果为空或字段不存在，如实说明，禁止推测
3. 结论部分区分"数据支持的事实"与"你的推测"，分开列出
```

**③ 抽查验证**

报告里挑 2~3 个关键数字，自己跑一遍 SQL 对一遍。这是你建立对智能体信任的最快方式——**验证三次之后，你就知道哪些类型的任务可以放心交给它**。

### text-to-SQL：让 AI 会查数据的技术

智能体查数据库的核心技术叫 **text-to-SQL**：把自然语言翻译成 SQL。现代做法不是让模型瞎写，而是三件套：

```
① Schema 注入：把相关表的建表语句、字段注释、示例行放进提示词
② 校验执行：生成的 SQL 先做语法校验，只读账号执行
③ 错误自愈：执行报错（字段名写错等）把报错喂回去，让它自己改
```

表格、日期计算、同比环比这些"数据分析师的体力活"，它做得又快又准；但**业务口径**（"活跃用户"的定义是 7 天内有登录还是 30 天内？）它不知道——**口径必须由你在提示词或数据字典里定义清楚**。

### 可视化与报告

拿到数字后，智能体可以继续：

- 用代码执行工具（Python）画图：趋势线、同比柱状图、品类占比
- 按"结论先行"的结构写报告：**核心发现 → 数据支撑 → 风险提示 → 建议行动**
- 导出成你需要的格式（HTML/PDF/PPT）

一个实用的提示词技巧：**先让它给"报告大纲"**，你确认大纲后再生成全文——避免 3000 字废话写完才发现方向不对。

### 一个真实的价值瞬间

某电商运营的日常：每周一上午花 3 小时拉各平台数据、做透视表、写周报。接入智能体后：周日晚配置好数据源与报告模板，周一早上 9 点智能体自动完成拉数、分析、出图、写稿，她花 20 分钟核对与润色。**她省下的 3 小时用来做了什么？研究下个月的营销策略——这才是人类该干的事。**

### 本章小结

- 数据分析智能体的流程：看表结构 → 查数 → 计算 → 可视化 → 出报告
- 防"编数据"三板斧：只读权限白名单、强制来源标注、人工抽查验证
- text-to-SQL 三件套：Schema 注入、校验执行、错误自愈
- 业务口径必须由人定义；智能体负责体力活，人类负责定义"什么是对的"
- 先审大纲再生成全文，避免方向性返工

## 让智能体值夜班

前两章的场景都是"你发起、它执行"。这一章讲更进一步：**事件驱动的自动化**——让智能体在后台值守，事件发生时自动出手。

### 一个典型工作流：邮件值守助手

```
触发：收到一封新邮件
  ↓
① 提取：解析邮件，识别是"客户咨询 / 内部通知 / 垃圾邮件"
  ↓
② 分诊：
   - 垃圾邮件 → 归档
   - 内部通知 → 按主题转发给对应同事
   - 客户咨询 → 继续 ↓
  ↓
③ 查证：从客户咨询中提取关键信息，去知识库/CRM 查询相关资料
  ↓
④ 起草：按公司话术模板起草回复
  ↓
⑤ 人在环上（Human-in-the-loop）：
   - 有把握的常见问题 → 直接发送
   - 涉及价格、合同、投诉 → 草稿发给你，等你一键确认
  ↓
⑥ 归档：记录本次处理，更新客户往来历史
```

注意第 ⑤ 步——**自动化不等于全自动**。成熟的工作流设计会在"低风险高确定性"处全自动，在"高风险低确定性"处设置人工确认点。

### 设计工作流的四个构件

| 构件 | 作用 | 例子 |
|------|------|------|
| **触发器** | 什么事件启动流程 | 收到邮件、定时到点、文件更新、监控告警 |
| **处理节点** | 智能体做什么 | 提取、分类、查询、生成、调用其他工具 |
| **条件分支** | 按情况走不同路 | 投诉类升级人工，常见类自动回复 |
| **人工确认点** | 高风险处暂停等确认 | 涉及付款、对外发送、删除操作 |

### 与传统 RPA/定时任务的差别

你可能会问：定时脚本早就有了，智能体版有什么不同？

- **传统脚本**：网页改版、邮件格式变化、多一个附件——脚本就崩了，等人来修
- **智能体工作流**：格式变了它会自适应（理解语义而非匹配格式），处理不了时**带着完整上下文升级给你**，而不是丢下一个报错码

一句话：**脚本处理"格式"，智能体处理"语义"**。流程越不稳定、变化越多，智能体的优势越大。

### 实操建议：从"周报自动化"起步

给零基础读者的第一个实践项目——自动化周报：

1. **周一到周五**：每天下班前花 30 秒，把当天做了什么丢给智能体记录（或让它读你的任务系统）
2. **周五下午**：触发器定时启动，智能体汇总本周记录，按你的周报模板生成草稿
3. **你做的**：读一遍、改两处、发送

这个项目的好处：风险极低（周报发错也就是尴尬一下）、收益直接、并且你会真实接触到"触发器 + 上下文累积 + 模板生成"三个核心概念。

### 边界：什么不要自动化？

三条红线：

1. **涉及钱的高风险操作**（付款、退款审批）——最多做到"生成待确认清单"
2. **对外公关内容**（官方声明、客诉公开回复）——发布权永远在人
3. **你自己都没想清楚规则的流程**——规则模糊的流程自动化出来的是"稳定的混乱"，先理清再自动

### 本章小结

## 内容生产的工业革命

一个人维护公众号/视频号/播客，最痛的不是写，而是**选题枯竭、资料搜集、格式排版**这些低创作含量的苦工。内容创作智能体的定位非常清晰：**它接管流水线，你负责灵魂**。

### 内容流水线全景

```
选题 → 调研 → 大纲 → 初稿 → 润色 → 配图 → 排版发布
  │       │       │      │      │
  人      智能体   人+AI  智能体  智能体
```

各环节的人机分工：

| 环节 | 谁主导 | 为什么 |
|------|--------|--------|
| 选题 | **人** | 方向感与受众洞察是创作者的核心价值 |
| 调研 | 智能体 | 搜集资料、整理观点、列参考来源——完美发挥 |
| 大纲 | 人 + AI | AI 出结构建议，人定逻辑主线 |
| 初稿 | 智能体 | 按大纲与素材成稿，人的时间留给改 |
| 润色 | 智能体 | 语病、节奏、标题党程度，AI 是校对之神 |
| 发布 | 人审核 | 事实核查 + 终审 |

### 实战演示：一篇深度文章的生产

**第一步：选题会（人）**
"我想写一篇讲智能体安全风险的文章，受众是有两年经验的开发者。"

**第二步：调研（智能体）**
提示词要点：给它受众画像、让它围绕"开发者视角"搜集真实案例与主流观点、**要求标注来源**、输出结构化的调研摘要。你花 10 分钟审读——这一步的质量决定文章的深度下限。

**第三步：大纲（人 + AI）**
AI 给出三版大纲，你把第二版的骨架和第三版的一个章节合并，并明确"第 3 节要放那个提示注入的案例"。

**第四步：初稿（智能体）**
把定稿大纲 + 调研摘要 + 你的两篇旧文章（风格样本）一起交给它。风格样本就是 Few-shot——**这比任何"写得有趣一点"的形容词都管用**。

**第五步：润色迭代（人 + 智能体）**
```
你：第二节的比喻太学术，换成程序员熟悉的类比
你：全文检查一遍：删掉所有"赋能""抓手"这类词
你：给每个小节写一个不落俗套的过渡句
```

全程人的实际投入约 60~90 分钟，产出质量与纯手写 4 小时的成品持平甚至更好——**因为你把 4 小时里的 3 小时苦工换成了 90 分钟的有效创作**。

### 事实核查：内容创作者的生死线

创作类任务不怕幻觉，但**事实性内容（数据、案例、引用）必须核查**。建立你的三步核查流：

1. 让智能体在调研阶段就标注每个事实的来源
2. 对将要发布的**每个具体数字与引用**二次验证（点开原始出处）
3. 文末保留"参考资料"清单——既是对读者负责，也是倒逼核查的机制

### 风格一致性：用"风格卡"克隆你自己

高级玩法——制作你的**风格卡**（Style Card）：

```
我的写作风格卡：
- 句子短，多用逗号节奏；专业术语首次出现给一句人话解释
- 每章开头用一个真实场景/故事切入，不写背景综述
- 表格优先于大段文字对比
- 自嘲式幽默点到为止，不玩梗堆砌
- 禁用词：赋能、抓手、闭环、底层逻辑（讽刺的是我总想用）
```

把风格卡和 2 篇代表作一起放进提示词，智能体的产出会立刻从"AI 味"变成"你味"。**风格卡是可以持续维护的资产：每次发现 AI 写得不像你，就往卡里加一条。**

### 本章小结

- 内容流水线的人机分工：人管选题与终审，AI 管调研、初稿、润色
- 调研要求标注来源，发布前逐条核查事实——这是内容创作者的生死线
- 风格样本（Few-shot）+ 风格卡是对抗"AI 味"的最有效武器
- 效率的本质不是写得快，而是把苦工外包、把时间还给真正的创作

## 从"提问"到"委托"的范式切换

课程 1 第 4 章教过提示词四要素。这一章把它升级为**任务委托**——与智能体交互，不再是简单的"提问-回答"，而是把任务完整地"外包"出去。这是提示工程的下一阶段范式。

### 对话式提示 vs 委托式提示

**❌ 对话式提示**（把智能体当搜索引擎用）：
```
"Python 的列表推导式怎么写？"
"那字典推导式呢？"
"能帮我写一个处理 JSON 的函数吗？"
"这个函数报错了：KeyError: 'name'"
```
—— 三轮下来你累了，它也只看到了碎片信息。

**✅ 委托式提示**（把智能体当专业承包商用）：
```
"读取 src/utils/data.py，将 process_data 函数重构为使用列表推导式，
 同时添加类型注解和单元测试，确保所有测试通过。"
```
—— 一句话，完整的任务书。

### 任务委托四要素（终极版）

```
┌─────────────────────────────────────────────┐
│  目标（Goal）     最终要达成什么，产出物是什么  │
│  约束（Constraints） 有哪些限制与禁止事项       │
│  上下文（Context）  相关的背景信息与环境信息    │
│  验收标准（Acceptance） 怎么算完成，如何验证    │
└─────────────────────────────────────────────┘
```

**模板（背下来）：**

```
目标：……（做成什么样，给谁用）
约束：……（不能做什么：不改接口/不加依赖/不超预算/合规要求）
上下文：……（技术栈/相关文件/历史决策/术语解释）
验收标准：……（测试通过/性能指标/覆盖率/审查要点）
```

**实战对比——同一个需求的三种写法：**

```
❌ 写法一（许愿式）："优化一下首页加载速度"
   → 它可能改缓存、可能删功能、可能换个框架——全凭心情

❌ 写法二（半成品）："优化首页加载速度，不改功能"
   → 方向对了，但"优化到什么程度算完"没有定义

✅ 写法三（委托式）：
   目标：优化首页加载速度
   约束：不改变现有功能，不引入新的依赖
   上下文：首页使用 React 18，后端是 FastAPI，数据库是 PostgreSQL，
          现状是首屏 3s，主要慢在首屏接口串行请求
   验收标准：首屏加载时间从 3s 降到 1s 以内，
            Lighthouse 性能分数 > 90，现有测试全部通过
```

### 四要素的常见盲区

| 要素 | 最常犯的错 | 补救问句 |
|------|-----------|---------|
| 目标 | 写了"做什么"没写"给谁用" | "这个产出物的使用者是谁？" |
| 约束 | 只写技术约束，忘了业务约束 | "有没有不能动的东西？合规要求？" |
| 上下文 | 假设它知道你的项目黑话 | "我提到的名词它都认识吗？" |
| 验收标准 | 写了"尽量快"这种不可判定的表述 | "我怎么机械地判断完成没完成？" |

**验收标准黄金法则：如果这条标准没法被自动化验证或快速人工判定，就重写它。**"尽量优化" ❌；"P99 < 500ms 且测试全过" ✅。

### 委托之后：怎么当"甲方"

委托不是甩手掌柜，专业甲方的三步闭环：

1. **计划确认**：对复杂任务，先让它出执行计划，你审计划再放行
2. **过程可见**：让它按阶段汇报（"完成 Schema 分析后暂停"），而不是两小时后见
3. **结果审查**：验收标准逐条打勾 + 抽查 20% 的关键 diff

以及最重要的心态：**第一次委托不完美是常态**。发现偏差不要推倒重来，用增量反馈修正——"方向对，但第 3 步应该用连接池而不是每次新建连接，改一下"。

### 本章小结

- 委托式提示 = 目标 + 约束 + 上下文 + 验收标准，一句话给全
- 最常被忽略的是约束与验收标准——"你没说的就是它发挥的空间"
- 验收标准黄金法则：可判定、可验证、最好可自动化
- 专业甲方三步闭环：审计划、看过程、查结果；用增量反馈修正偏差

## 信任是攒出来的，不是设出来的

到了实战篇的最后一章，聊一个比技术更重要的话题：**你对智能体的信任应该怎么建立**。信任崩塌有两种经典方式——一次性放权后被坑到崩溃（再也不用了），或者全程手动确认（累到放弃，智能体沦为聊天玩具）。这一章教你走第三条路。

### 信任阶梯：从低风险到高杠杆

正确的放权路径是一条阶梯：

```
第 1 阶段：只读任务
  "分析这段代码的问题" "总结这份文档" "查一下这个报错的原因"
  → 输出不落盘，看对看错都无害，重点建立"能力边界感"

第 2 阶段：可逆写操作
  "写个测试文件" "改这个函数并跑测试" "生成一份草稿"
  → 有 git/回收站兜底，错了能回滚，重点验证"反思与自愈能力"

第 3 阶段：审批式写操作
  "重构这个模块（先出计划我审批）" "生成报告（发布前我确认）"
  → 智能体提案、人类拍板，重点磨合"任务委托四要素"

第 4 阶段：受控自主
  "每周一自动生成数据周报并发我" "PR 通过测试自动合并到开发分支"
  → 带护栏的全自动，护栏 = 本章第二节
```

每上一个台阶的资格，都要靠**下一个台阶的稳定表现**来挣。反过来，一旦某个阶段出现连续失败，就退回上一阶——这不是倒退，是止损。

### 护栏设计：四道防线

当任务进入"受控自主"阶段，用四道防线兜底：

**① 权限护栏（事前）**
最小权限原则：只读账号、白名单目录、独立 API Key、消费限额。智能体再聪明，物理上做不了权限外的事。

**② 确认护栏（事中）**
维护一份**高危操作清单**，命中即暂停请求人工确认：

```
高危操作清单（示例）：
- 删除超过 10 个文件 / 任何 git push --force
- 对外发送邮件 / 调用付费 API 超过单次预算
- 修改生产配置 / 数据库写操作（只读分析除外）
- 安装新的系统依赖
```

**③ 审计护栏（事后）**
所有智能体操作留日志：执行了什么命令、改了哪些文件、调用了什么 API、消耗多少 Token。出问题能回溯，复盘能改进。

**④ 熔断护栏（兜底）**
最大步数、最大预算、超时熔断、连续失败即停——第 4 章讲过的循环终点线，在这里升级为"全局预算管理"。

### 审查的效率化：别当"逐行阅读的审查员"

人的审查时间有限，按风险分层审查：

| 改动类型 | 审查方式 |
|---------|---------|
| 格式化、注释、文档 | 扫一眼 diff 统计（不看细节） |
| 业务逻辑修改 | 看关键 diff + 验证测试覆盖 |
| 安全/权限/数据相关 | 逐行细看 + 人工测试 |
| 全新的架构决策 | 必须人做，智能体只提供材料 |

**审查的重点不是"每行代码对不对"，而是"方向和边界对不对"。**

### 一个心态转折：从"工具"到"同事"

最后分享一个多数资深用户的共识：把智能体当**工具**用，你会一直用不顺手（工具的隐喻=按一下动一下）；当**不知疲倦但需要管理的同事**用，一切技巧都顺理成章——

- 你会给新同事写清楚任务背景（上下文）
- 你会让新人先出方案再动手（计划确认）
- 你会检查他的产出而不是假设完美（结果审查）
- 你会把踩过的坑沉淀成团队规范（记忆系统）
- 你会逐步给他更重要的任务（信任阶梯）

**智能体不是要取代人，而是成为人的超级助手。人类：定义目标、设定边界、做关键决策；智能体：执行细节、处理重复劳动、提供建议。人类始终掌握最终决策权。**

### 本章小结

- 信任阶梯四阶段：只读 → 可逆写 → 审批式写 → 受控自主，台阶靠表现挣
- 四道护栏：权限（事前）、确认（事中）、审计（事后）、熔断（兜底）
- 审查按风险分层，重点看"方向与边界"而非逐行
- 心态升级：从工具到同事——组织管理的智慧全部适用

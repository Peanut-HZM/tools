## 柳暗花明！

当我发现 rules 的时候，感觉就像发现了新大陆！

### 什么是 Rules？

Rules 是一组规则文件，用来规范 AI 的行为。它告诉 AI：

- ✅ **应该做什么**
- ❌ **不应该做什么**
- 📋 **如何思考和行动**

### Rules 为什么有效？

AI 模型在生成回应时，会优先考虑最近的、明确的指令。Rules 就是预先设置的明确指令，让 AI 在每次回应前都"记住"这些约束。

**工作原理**：

1. **上下文注入**：Rules 作为系统上下文的一部分被注入到每次对话中
2. **优先级处理**：AI 会优先遵循 Rules 中的指令
3. **行为约束**：Rules 限定了 AI 的输出范围和行为模式

### Rules 编写指南

#### 基本结构

```markdown
# AI 助手行为规范

## 章节标题

1. **具体规则**：规则内容
2. **另一条规则**：规则内容
```

#### 语法规范

- 使用清晰的标题
- 使用编号列表
- 每条规则应该是可执行的
- 避免模糊的词汇（如"可能"、"尽量"）

#### 最佳实践

1. **具体**：不要说"保持代码质量"，要说"遵循 PEP8 规范"
2. **可执行**：规则应该是 AI 能够执行的
3. **有优先级**：重要规则放在前面
4. **覆盖常见场景**：预先考虑常见场景并设置规则

### 我的第一条 Rules

```markdown
# AI 助手行为规范

## 代码修改原则

1. **最小化修改**：只修改我明确要求修改的部分
2. **不要擅自添加**：不要添加我未要求的功能
3. **保持原有风格**：保持代码的原有风格和格式
4. **说明变更**：修改前先告诉我改了哪里

## 代码质量要求

1. 添加必要的注释
2. 遵循项目的代码规范
3. 考虑边界情况
```

### 使用 Rules 后的变化

| 之前 | 后 |
|------|------|
| AI 乱改一堆代码 | 只改我要求的地方 ✅ |
| 需要大量 review | 改动清晰，快速 review ✅ |
| 经常要反复修正 | 第一次就做对 ✅ |
| 感觉 AI 很笨 | 感觉 AI 变聪明了 ✅ |

### 实战示例

#### 通用 Rules 示例

```markdown
# 通用 Rules

## 回应原则

1. 先理解问题，再给出答案
2. 如果不确定，请说明
3. 提供代码时，添加必要的注释

## 代码修改原则

1. 最小化修改
2. 不要擅自添加功能
3. 保持原有代码风格
```

#### 前端 Rules 示例

```markdown
# 前端开发 Rules

## React 组件规范

1. 使用函数组件
2. 使用 TypeScript
3. 使用 Tailwind CSS 进行样式设计

## 命名规范

1. 组件名使用 PascalCase
2. 函数名使用 camelCase
3. 常量名使用 UPPER_SNAKE_CASE
```

#### 后端 Rules 示例

```markdown
# 后端开发 Rules

## API 设计规范

1. 使用 RESTful 风格
2. 返回统一的响应格式
3. 使用适当的 HTTP 状态码

## 数据安全

1. 验证所有输入
2. 使用参数化查询防止 SQL 注入
3. 敏感信息使用环境变量
```

### 效果对比

**Before (没有 rules)**:

```
用户：修改 login 函数的密码验证
AI：改了 50 个文件，包括一些不该改的...
```

**After (有 rules)**:

```
用户：修改 login 函数的密码验证
AI：好的，我只修改了 login 函数中的密码验证逻辑，变更如下：
- 第 10 行：添加了密码长度检查
- 第 15 行：添加了特殊字符检查
```

## 测验：Rules 应用测验

**及格分数**: 60


### 问题 1

Rules 的主要作用是什么？
- [ ] 让代码运行更快
- [ ] 自动生成代码
- [x] 规范 AI 的行为模式
- [ ] 美化代码格式

**答案**: 2
**解析**: Rules 的核心作用是规范 AI 的行为模式。


### 问题 2

Rules 的核心作用是什么？
- [ ] 让代码运行更快
- [x] 规范 AI 的行为
- [ ] 自动修复 bug
- [ ] 生成单元测试

**答案**: 1
**解析**: Rules 的主要作用是规范 AI 的行为，让 AI 按照预设的规则进行回应。


### 问题 3

以下哪些内容适合放入 Rules？（多选）
- [x] 代码风格和规范
- [x] 具体的业务逻辑
- [ ] 今天的天气
- [x] 沟通方式和偏好

**答案**: 0,1,3
**解析**: 代码规范、沟通偏好、项目约束都是 Rules 的内容，但业务逻辑不应该放在 Rules 中。


### 问题 4

好的 Rules 应该具备哪些特点？（多选）
- [x] 具体明确
- [x] 可执行
- [ ] 越复杂越好
- [x] 有优先级

**答案**: 0,1,3
**解析**: 好的 Rules 应该具体明确、可执行、有优先级。模糊的规则无法有效约束 AI。


### 问题 5

以下哪条 Rules 写得最好？
- [ ] 保持代码质量
- [ ] 写出好的代码
- [x] 遵循 PEP8 规范，使用 4 空格缩进
- [ ] 尽量写得简洁

**答案**: 2
**解析**: 第 3 条规则具体明确，给出了具体的代码风格要求，是可执行的好规则。


### 问题 6

当你想要 AI 只修改指定文件而不改动其他文件时，应该使用哪条 Rules？
- [ ] 请小心修改
- [x] 只修改我指定的文件，不要改动其他文件
- [ ] 修改代码时要注意
- [ ] 不要改太多东西

**答案**: 1
**解析**: 这条规则明确约束了 AI 的修改范围，是最有效的。

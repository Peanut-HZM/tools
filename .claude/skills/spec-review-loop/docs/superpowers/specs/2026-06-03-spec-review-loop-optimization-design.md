# spec-review-loop 技能优化设计

- 日期：2026-06-03
- 范围：对现有 `spec-review-loop` 技能进行全面优化
- 目标：解决四个实际痛点（发现范围不准、循环终止不稳定、清单没被真正执行、修改边界模糊），并将技能重构为「通用核心 + 技术栈插件」的分层架构

---

## 一、背景与问题

现有技能由 `SKILL.md` 和 `references/review-checklist.md` 两个文件组成，已覆盖发现范围、四个审查维度、循环终止、风险分级和报告格式。但在实际使用中存在四个痛点：

1. **发现范围不准**：从对话上下文提取待审文件路径不可靠，易漏扫或扫到无关内容。
2. **循环终止不稳定**：「是否有新发现」靠记忆和感觉判断，会提前停止，或反复报告同一问题凑轮数。
3. **清单没被真正执行**：清单是「参考资料」，没有强制对照动作，实际审查凭感觉扫一遍。
4. **修改边界模糊**：高/中/低风险靠临场判断，导致该确认的直接改了、不该改的又改了。

此外，现有清单高度绑定 Java / Spring / MyBatis / MySQL 技术栈，但技能名称与描述是通用的，二者存在张力。

**根因归纳**：四个痛点的共同根因是「循环过程没有持久化状态」——发现靠记忆、轮次靠感觉、清单靠自觉、边界靠临场判断。

---

## 二、设计目标

1. 引入**持久化发现台账**，把发现、去重、终止判断从「靠记忆」变为「靠文件状态」，确定性可回溯。
2. 重构为**分层架构**：核心流程语言无关；维度 1/2 变为可插拔的技术栈插件；维度 3/4 归入通用核心。
3. 把清单审查从「参考」变为「强制三态裁决（✅/⚠️/⊘）」，发现必须附 `文件:行号` 证据。
4. 用**正面白名单**取代模糊的高/中/低风险判断，消除灰色地带。

---

## 三、架构：分层后的文件结构

```
spec-review-loop/
├── SKILL.md                          # 语言无关核心：发现 → 台账 → 循环 → 报告 → 边界
├── references/
│   ├── checklist-core.md             # 维度3(SQL/数据安全)、维度4(设计完整性) —— 通用
│   ├── checklist-java-spring.md      # 维度1、2 的 Java/Spring/MyBatis 专属项（现有清单迁移）
│   └── stack-detection.md            # 技术栈识别规则：决定加载哪个栈插件
```

### 3.1 分层归属

| 维度 | 归属 | 理由 |
|------|------|------|
| 维度 1：项目规范符合性 | 栈插件 `checklist-java-spring.md` | 强绑技术栈（Controller 无逻辑、LambdaQueryWrapper、@Schema 等） |
| 维度 2：现有功能安全性 | 栈插件 `checklist-java-spring.md` | 强绑技术栈（Bean 注入冲突、Mapper XML、N+1 等） |
| 维度 3：SQL 幂等性与数据安全 | 通用核心 `checklist-core.md` | SQL 幂等、ON DUPLICATE KEY、回滚等不绑特定后端语言 |
| 维度 4：设计完整性与一致性 | 通用核心 `checklist-core.md` | 占位符、前后端契约、回滚方案等语言无关 |

### 3.2 技术栈识别（stack-detection.md）

技能启动时按项目特征识别技术栈并加载对应插件：

| 特征文件 | 判定栈 | 加载插件 |
|----------|--------|----------|
| `pom.xml` / `build.gradle` / `build.gradle.kts` | Java/Spring | `checklist-java-spring.md` |
| （未来扩展）`package.json` | 前端 | `checklist-frontend.md` |
| （未来扩展）`pyproject.toml` / `requirements.txt` | Python | `checklist-python.md` |

- 命中多个特征时，加载所有命中的栈插件。
- 未命中任何栈插件时，**仅执行通用核心清单（维度 3、4）**，并在报告中提示「未识别到技术栈插件，仅执行通用审查」。
- 维度 1、2 在无栈插件时整体标记为 ⊘ N/A。

### 3.3 可扩展性

新增技术栈支持时，只需新增一个 `checklist-<stack>.md` 并在 `stack-detection.md` 增加一条识别规则，**核心流程与 `SKILL.md` 一字不改**。

## 四、发现台账机制

审查开始时在 `docs/reviews/YYYY-MM-DD-<topic>-review.md` 创建台账文件，整个循环读写它。台账是解决「发现范围不准」与「循环终止不稳定」的支柱。

### 4.1 台账文件位置

- 默认固定写入 `docs/reviews/`，目录不存在时自动创建。
- 选择固定路径而非就近存放：审查产物与设计产物分离更清晰，固定路径便于回溯。
- 用户偏好的审查产物位置可覆盖此默认值。

### 4.2 台账结构

```markdown
# 审查台账：<topic>  (YYYY-MM-DD)

## 待审清单（启动时确认）
- [x] docs/plans/2026-06-03-xxx-design.md
- [x] sql/V20260603__add_user.sql
- [ ] (用户增删)

## 发现表
| ID  | 维度 | 严重 | 文件:行 | 问题 | 状态 | 发现轮次 |
|-----|------|------|---------|------|------|----------|
| F01 | 3-SQL | 高 | V20260603:12 | CREATE TABLE 无 IF NOT EXISTS | 已修复 | 1 |
| F02 | 4-设计 | 中 | design.md:40 | 回滚方案缺失 | 待确认 | 1 |

## 轮次日志
- 第1轮：新增 F01、F02；修复 F01；连续无发现计数 = 0
- 第2轮：新增 0；F02 待用户确认；连续无发现计数 = 1
- 第3轮：新增 0；连续无发现计数 = 2 → 达到终止条件，审查结束
```

### 4.3 发现条目固定字段

- **ID**：稳定标识（F01、F02…），全程不变，用户可按 ID 回复决策。
- **维度**：1/2/3/4。
- **严重**：高 / 中 / 低（定义见第六节）。
- **文件:行**：证据定位，⚠️ 发现项必填。
- **问题**：一句话描述。
- **状态**：待修复 / 已修复 / 待确认 / 已忽略。
- **发现轮次**：首次发现于第几轮。

### 4.4 台账驱动的三个机制

1. **发现范围确认**：扫描后先把「待审清单」写入台账并停下，让用户确认增删，确认后才开审。
   - 来源优先级：`git status` / `git diff`（最可靠） > 对话上下文提到的路径 > 按日期扫描兜底（今天/昨天的 `*design*.md`、`*implementation-plan*.md`、openspec 变更、新增/修改的 SQL）。
2. **确定性终止判断**：每轮新发现先去台账查重——同 `文件:行号` 同类问题视为重复，不写入、不计新发现。「本轮新增条目数 == 0」才算无发现；连续 2 轮新增为 0 即停。不再靠感觉，也无法靠重复报告凑轮数。
3. **有据可查的去重**：判重比对台账已有行，而非依赖记忆。

## 五、循环流程与清单三态裁决

把每个维度的审查变为**必须产出的裁决记录**，没有裁决就不算审完该维度，从而解决「清单没被真正执行」。

### 5.1 三态裁决

核心/栈插件清单的每个检查项都要落一个判定：

- ✅ **通过**：检查了，无问题。
- ⚠️ **发现**：有问题 → **必须附 `文件:行号` 证据**，并写入台账发现表。无证据的「感觉有问题」不允许写入台账。
- ⊘ **N/A**：本次无相关内容（如本次未改动 SQL，则维度 3 整体 N/A）。

显式区分「N/A 跳过」与「✅ 通过」，避免混为一谈。

### 5.2 单轮流程

```
第 N 轮：
  1. 重新读取台账 + 所有待审内容（含上一轮的修改）
  2. 加载适用的栈插件（首轮已识别）
  3. 按维度 1→2→3→4 逐项裁决：
     - 每项标 ✅/⚠️/⊘
     - ⚠️ 项：查台账判重 → 新问题写入发现表（带文件:行号）
  4. 执行修改：
     - 白名单内 → 直接改，台账状态置「已修复」
     - 白名单外 → 报告，台账状态置「待确认」
  5. 写轮次日志：本轮新增 N 条、修复 M 条
  6. 判定：本轮新增 == 0 ? 连续无发现 +1 : 连续无发现清零
终止：连续 2 轮新增为 0  |  上限 10 轮
```

### 5.3 裁决粒度（避免报告过长）

- 要求 Claude **对每个维度逐项在内部走一遍**。
- 报告中**只呈现 ⚠️ 发现项和 ⊘ 整体 N/A 的维度**；✅ 项归并为「维度 X：N 项通过」。
- 既保证真正走了清单，又不淹没报告。

## 六、修改边界白名单

用正面白名单取代「高/中/低」临场判断，解决「修改边界模糊」。核心规则：**不在白名单内 = 高风险 = 先报告后确认。**

### 6.1 可直接修改白名单（穷举，只增不模糊）

- 补充注释、文档措辞、`@Schema`/`@Tag` 等纯文档性注解。
- 修正拼写、格式、缺失的 import。
- SQL 纯幂等性加固（不改数据语义）：补 `IF NOT EXISTS`/`IF EXISTS`、给种子 INSERT 补 `ON DUPLICATE KEY UPDATE`、补显式字段列表、补合理 `DEFAULT`。
- 填写文档中的 TBD/TODO 占位符（内容可从上下文 100% 明确推断时）。

### 6.2 白名单外一律先确认（默认行为）

- 任何改变业务逻辑、执行路径、方法签名的修改。
- 删除/重写既有逻辑、架构性调整。
- 改动 `WHERE` 条件、涉及既有数据的 DML、外键约束。
- 任何无法从上下文 100% 确定意图的占位符填写。

### 6.3 严重程度定义（保留并明确）

- **高**：可能导致现有功能异常、数据丢失、SQL 不可重复执行。
- **中**：违反项目规范但不会导致功能异常。
- **低**：补充注释、完善文档等非功能性改进。

## 七、报告格式

在现有报告结构上增强：

1. **顶部总体结论**：一句话概括。例：「审查 3 轮，发现 5 项，已修复 3 项，待确认 2 项，其中 1 项高风险待决策。」
2. **台账驱动**：报告由台账生成。
3. **待确认项单独成节并编号**：每条给出建议动作与影响，方便用户按 ID 逐条回复（如「F02 同意改 / F04 不改」）。
4. **保留原有专项小节**：SQL 幂等性专项确认、现有功能安全性专项确认。

报告骨架：

```markdown
## 审查报告

### 总体结论
审查 N 轮，发现 Y 项，已修复 Z 项，待确认 W 项，其中 H 项高风险待决策。

### 各轮详情
**第 1 轮**（新增 A 项）
- [维度][严重] F01 问题描述 → 修复动作

### 待确认项（需用户决策）
- **F02**[中][维度4] 问题：回滚方案缺失（design.md:40）
  - 建议动作：补充回滚 SQL 段
  - 影响：仅文档变更，无运行时影响

### SQL 幂等性专项确认
- ✅/❌ 文件名：说明

### 现有功能安全性专项确认
- ✅/❌ 说明
```

## 八、与现有技能的协作（不变）

- **brainstorming**：在其完成后独立调用，不嵌入其流程。
- **writing-plans**：审查范围包含其输出的实现计划文档。
- **skill-creator**：仅用于创建/修改本技能本身。

## 九、变更清单（落地时执行）

1. 新建 `references/checklist-core.md`：迁入现有清单的维度 3、4，去除 Java 专属措辞使其语言无关。
2. 新建 `references/checklist-java-spring.md`：迁入现有清单的维度 1、2，原样保留全部 Java/Spring/MyBatis 检查项。
3. 新建 `references/stack-detection.md`：技术栈识别规则表 + 未命中时的降级策略。
4. 删除原 `references/review-checklist.md`（内容已拆分迁移）。
5. 重写 `SKILL.md`：
   - 概述与 description 改为语言无关表述（保留中文）。
   - 发现机制改为台账驱动 + 启动确认 + 来源优先级。
   - 新增「技术栈识别与插件加载」段。
   - 循环流程改为三态裁决 + 确定性终止。
   - 修改边界改为正面白名单。
   - 报告格式增加总体结论与待确认项编号节。

## 十、验收标准

- 在无技术栈特征的目录运行时，仅执行维度 3、4 并正确提示降级。
- 在含 `pom.xml` 的目录运行时，自动加载 Java 插件，执行全部 4 维度。
- 每次运行生成一份台账文件，含待审清单、发现表、轮次日志。
- 循环在「连续 2 轮新增为 0」时确定性终止，重复报告同一问题不会增加轮数。
- 白名单外的修改不会被直接执行，而是进入待确认节。

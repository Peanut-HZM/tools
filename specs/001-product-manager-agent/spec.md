## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一句话需求生成完整PRD (Priority: P1)

作为初创团队创始人，我输入"我想做个记账软件"这样的一句话需求，Agent能够通过多轮对话引导我思考产品的各个方面（目标用户、核心场景、商业模式等），最终生成一份结构完整、可直接落地的PRD文档。

**Why this priority**: 这是产品的核心价值主张，降低非专业产品人员产出高质量需求文档的门槛，是用户最直接的使用场景。

**Independent Test**: 用户可以仅通过一句话输入，经过10-15轮对话交互，最终获得包含产品背景、竞品分析、功能架构、用户流程、非功能需求等完整章节的PRD文档。

**Acceptance Scenarios**:

1. **Given** 用户在对话界面输入"我想做个记账软件", **When** Agent接收到输入, **Then** Agent应该识别这是一句话需求并进入引导模式，提出3-5个关键澄清问题（如目标用户、差异化定位、商业模式等）

2. **Given** 用户回答Agent提出的澄清问题, **When** 用户完成所有关键信息的提供, **Then** Agent应该自动进入竞品分析阶段，搜索同类产品并生成对比表格

3. **Given** 竞品分析已完成, **When** 用户确认或修改竞品分析结果, **Then** Agent应该生成功能架构图、用户流程图，并最终输出完整PRD文档

4. **Given** PRD文档已生成, **When** 用户要求导出, **Then** 系统应该支持导出为Markdown、PDF或Word格式

---

### User Story 2 - 上传现有文档进行补全 (Priority: P2)

作为技术开发者，我已经有一个初步的功能列表文档，但缺乏产品经验，需要Agent帮我识别缺失信息并补全成完整的PRD。

**Why this priority**: 满足已有部分需求的用户群体，帮助他们系统化梳理和补全需求，扩大产品的适用场景。

**Independent Test**: 用户可以上传Markdown、Word或PDF格式的现有文档，Agent自动解析并识别缺失的关键信息，然后通过对话引导用户补充，最终生成完整PRD。

**Acceptance Scenarios**:

1. **Given** 用户上传了一个只有功能列表的Markdown文档, **When** 文档上传成功, **Then** Agent应该解析文档内容，识别出缺失的关键信息（目标用户画像、使用场景、优先级等）并以结构化方式呈现给用户

2. **Given** Agent已识别出缺失信息, **When** 用户选择需要补充的部分, **Then** Agent应该通过引导式提问帮助用户完善该部分内容

3. **Given** 用户已完成缺失信息的补充, **When** 用户要求生成完整PRD, **Then** Agent应该整合原有内容和新增内容，生成结构完整的PRD文档

4. **Given** PRD已生成, **When** 用户对某个模块提出修改意见, **Then** Agent应该支持局部修改而不影响其他已确认的内容

---

### User Story 3 - 多轮迭代优化PRD (Priority: P3)

作为初级产品经理，我已经通过Agent生成了PRD初稿，但需要根据团队反馈进行多轮修改和版本管理。

**Why this priority**: 满足专业用户的迭代需求，支持PRD的持续优化和版本追踪，提升产品的专业性和实用性。

**Independent Test**: 用户可以基于已生成的PRD进行多轮对话修改，系统记录所有版本变更，支持版本对比和回滚。

**Acceptance Scenarios**:

1. **Given** 用户已有生成的PRD文档, **When** 用户在对话中提出"帮我完善异常流程部分", **Then** Agent应该针对异常流程部分进行深入追问并生成补充内容

2. **Given** 用户对PRD进行了修改, **When** 修改完成后, **Then** 系统应该自动保存为新版本，并在侧边栏显示版本历史

3. **Given** 用户想查看不同版本的差异, **When** 用户选择两个版本进行对比, **Then** 系统应该以diff视图展示两个版本之间的差异

4. **Given** 用户想回滚到某个历史版本, **When** 用户选择目标版本并确认回滚, **Then** 系统应该将当前PRD恢复到该版本状态

---

### User Story 4 - 后台管理大模型配置 (Priority: P1)

作为系统管理员，我需要在后台管理中配置大模型API的基本信息（baseUrl、apiKey等），确保产品可以调用市面上主流的大模型供应商接口。

**Why this priority**: 这是实现产品核心功能的技术基础，确保系统具备灵活的大模型接入能力，支持不同供应商的切换和配置。

**Independent Test**: 管理员可以在后台管理页面添加、编辑、删除大模型配置，包括baseUrl、apiKey、模型名称等，配置完成后前端对话功能可以正常调用大模型API。

**Acceptance Scenarios**:

1. **Given** 管理员进入后台管理的系统设置页面, **When** 管理员点击"添加大模型配置", **Then** 系统应该弹出表单，允许输入配置名称、baseUrl、apiKey、模型名称、供应商类型等字段

2. **Given** 管理员已添加多个大模型配置, **When** 管理员查看配置列表, **Then** 系统应该显示所有配置，并允许编辑或删除每个配置

3. **Given** 存在有效的大模型配置, **When** 前端用户在产品经理Agent界面进行对话, **Then** 系统应该能够成功调用配置的大模型API并返回响应

4. **Given** 某个大模型配置失效（如apiKey过期）, **When** 系统调用该模型失败, **Then** 系统应该自动切换到备用配置或给出明确的错误提示

---

### Edge Cases

1. **What happens when 用户输入完全不相关的内容（如"今天天气怎么样"）？**
   - Agent应该友好地引导用户回到产品需求讨论，提示"我是产品经理助手，专注于帮助您完善产品需求。请告诉我您想做什么产品？"

2. **How does system handle 大模型API调用超时或失败？**
   - 系统应该显示"服务暂时不可用，请稍后重试"的友好提示，并提供"重新生成"或"简化需求"的选项

3. **What happens when 用户上传的文档格式不支持或文件损坏？**
   - 系统应该提示"不支持的文件格式，请上传Markdown、Word或PDF格式的文档"，并允许重新上传

4. **How does system handle PRD生成过程中用户刷新页面？**
   - 系统应该自动保存对话上下文和中间状态，用户重新进入后可以恢复到之前的进度

5. **What happens when 用户连续多次要求修改同一部分内容？**
   - 系统应该记录每次修改的版本，允许用户查看历史版本并选择最满意的一版

6. **How does system handle 大模型返回的内容包含不当信息？**
   - 系统应该设置内容安全过滤机制，对不当内容进行拦截并提示"生成内容可能包含不当信息，请重新描述您的需求"

7. **What happens when 用户达到大模型API调用限流上限？**
   - 系统应该显示"您已达到本小时的调用上限，剩余等待时间XX分钟"，并建议用户"查看已生成的PRD"或"稍后再试"

8. **How does system handle 用户短时间内大量重复调用？**
   - 系统应该实施防抖机制，同一用户在30秒内对同一功能的重复调用应该被合并或拒绝，并提示"请求过于频繁，请稍后再试"

## Requirements *(mandatory)*

### Functional Requirements

#### 核心对话功能

- **FR-001**: System MUST 支持用户通过自然语言输入产品需求想法，Agent能够识别输入类型（一句话需求、部分需求、完整文档）并进入相应的工作模式

- **FR-002**: System MUST 支持多轮对话交互，Agent能够根据当前阶段和上下文提出针对性的澄清问题，每次提问不超过3个问题

- **FR-003**: System MUST 支持文档上传功能，允许用户上传Markdown、Word、PDF格式的现有需求文档，并自动解析提取关键信息

- **FR-004**: System MUST 在对话过程中展示当前处理阶段（需求理解、市场研究、架构设计、详细设计、整合输出）和进度指示

- **FR-005**: System MUST 支持对话历史记录，用户可以随时查看之前的对话内容

#### 竞品分析功能

- **FR-006**: System MUST 能够根据用户描述的产品需求自动搜索相关竞品（3-5个），并提取竞品的核心功能、优缺点信息

- **FR-007**: System MUST 生成结构化的竞品分析表格，包含竞品名称、核心功能、优点、缺点、我们的机会等字段

- **FR-008**: System MUST 基于竞品分析提供3-5个差异化功能建议，帮助用户找到产品的独特价值主张

#### PRD生成功能

- **FR-009**: System MUST 能够根据对话内容和竞品分析结果生成标准化的PRD文档，包含以下章节：项目背景、竞品分析、产品架构、功能需求、非功能需求、数据需求、版本规划、附录

- **FR-010**: System MUST 在PRD中使用Mermaid语法自动生成业务流程图、用户流程图、状态图等可视化图表

- **FR-011**: System MUST 为每个功能点定义清晰的验收标准，确保需求可量化、可测试

- **FR-012**: System MUST 支持PRD的实时预览功能，用户可以在对话界面中查看生成的PRD内容

#### PRD管理与导出

- **FR-013**: System MUST 支持PRD的版本管理，自动保存每次生成的版本，并记录版本号和生成时间

- **FR-014**: System MUST 支持版本对比功能，以diff视图展示不同版本之间的差异

- **FR-015**: System MUST 支持PRD导出功能，允许用户导出为Markdown、PDF、Word格式

- **FR-016**: System MUST 支持PRD的局部修改，用户可以针对特定章节提出修改意见而不影响其他部分

#### 后台管理-大模型配置

- **FR-017**: System MUST 在后台管理-系统设置中提供大模型配置管理功能，允许管理员添加、编辑、删除大模型配置

- **FR-018**: System MUST 支持配置以下大模型参数：配置名称、baseUrl、apiKey、模型名称、供应商类型（如OpenAI、Anthropic、Azure、国内厂商等）

- **FR-019**: System MUST 支持配置请求参数：temperature、maxTokens、timeout等高级参数

- **FR-020**: System MUST 支持测试连接功能，管理员可以验证配置的baseUrl和apiKey是否有效

- **FR-021**: System MUST 支持设置默认模型配置和备用模型配置，当主配置失效时自动切换

- **FR-022**: System MUST 支持查看大模型调用的统计信息：调用次数、响应时间、token消耗、错误率等

#### 安全与隐私

- **FR-023**: System MUST 使用 AES-256 加密算法加密存储所有大模型 API Key，加密密钥通过环境变量注入，禁止硬编码在代码或配置文件中

- **FR-024**: System MUST 确保 API Key 只在服务端解密和使用，禁止将明文 API Key 传输到前端或记录到日志中

- **FR-025**: System MUST 对包含敏感信息（如 API Key）的数据库字段启用加密存储，防止数据库泄露导致密钥暴露

#### 用户界面

- **FR-027**: System MUST 采用三栏布局（侧边栏、对话主区域、工具栏），侧边栏包含历史会话列表和PRD版本管理

- **FR-028**: System MUST 支持响应式设计，在桌面端（≥1280px）、平板端（768px-1279px）、移动端（<768px）自适应布局

- **FR-029**: System MUST 在对话界面显示快捷操作按钮，如"@分析竞品"、"@生成流程图"、"@查看PRD"、"@导文档"等

- **FR-030**: System MUST 支持深色模式和浅色模式切换

#### 数据保留与归档

- **FR-031**: System MUST 自动保留对话历史和PRD文档90天，超过90天的数据自动归档到冷存储，归档数据仍支持查询和导出

- **FR-032**: System MUST 在数据归档前7天向用户发送通知，提示用户及时导出重要文档

- **FR-033**: System MUST 支持管理员配置数据保留策略（最短30天，最长365天），满足不同合规要求

#### 并发控制

- **FR-034**: System MUST 实现乐观锁机制处理并发编辑冲突，每次保存时检查版本号，如果检测到冲突（其他用户已更新），提示用户并显示冲突内容

- **FR-035**: System MUST 在检测到编辑冲突时提供"覆盖保存"、"放弃修改"、"合并内容"三个选项供用户选择

- **FR-036**: System MUST 在会话列表中显示"当前有人正在编辑"的状态指示，当其他设备/浏览器正在编辑同一会话时给予提示

#### 限流与配额

- **FR-037**: System MUST 实现分级限流策略：普通用户每小时最多50次大模型API调用，高级用户每小时最多200次调用

- **FR-038**: System MUST 在接近限流阈值时向用户发送警告提示（剩余10次时），告知重置时间

- **FR-039**: System MUST 在达到限流上限时返回友好提示"您已达到本小时的调用上限，请稍后重试或升级账户"，并显示剩余等待时间

- **FR-040**: System MUST 在后台管理提供限流配置界面，允许管理员调整不同用户级别的配额限制

### Key Entities

- **会话（Conversation）**: 代表一次完整的产品需求讨论过程，包含会话ID、创建时间、最后更新时间、会话标题、当前阶段、关联的用户ID、版本号（乐观锁使用）

- **消息（Message）**: 代表会话中的一条对话记录，包含消息ID、会话ID、发送者类型（用户/Agent）、消息内容、消息类型（文本/结构化内容/图表）、发送时间

- **PRD文档（PRDDocument）**: 代表生成的产品需求文档，包含文档ID、会话ID、版本号、文档内容（Markdown格式）、生成时间、状态（草稿/已确认/已归档）
  - **状态流转**: 草稿 → 已确认 → 已归档（90天后自动归档）

- **竞品分析（CompetitorAnalysis）**: 代表竞品分析结果，包含分析ID、会话ID、竞品列表（名称、功能、优缺点）、差异化建议、生成时间

- **大模型配置（LLMConfig）**: 代表大模型API的配置信息，包含配置ID、配置名称、供应商类型、baseUrl、apiKey、模型名称、请求参数、是否默认、是否启用、创建时间

- **用户（User）**: 使用产品经理Agent的用户，包含用户ID、用户名、角色（普通用户/管理员）、创建时间、用户级别（普通/高级）、当前小时API调用次数、限流重置时间

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户可以从一句话需求开始，在20轮对话内获得一份包含至少8个标准章节（项目背景、竞品分析、产品架构、功能需求、非功能需求、数据需求、版本规划、附录）的完整PRD文档

- **SC-002**: 竞品分析功能能够针对用户描述的产品需求，在30秒内返回至少3个相关竞品的结构化分析报告

- **SC-003**: PRD文档的质量检查通过率达到80%以上，即80%的生成文档包含清晰的产品定位、明确的目标用户画像、完整的功能架构、详细的用户流程、全面的异常场景考虑

- **SC-004**: 系统支持至少5种主流大模型供应商的API接入（如OpenAI、Anthropic、Azure OpenAI、百度文心、阿里通义等），管理员可以在后台自由切换配置

- **SC-005**: 大模型API的平均响应时间不超过10秒，95%的请求在15秒内返回结果

- **SC-006**: 用户可以对生成的PRD进行至少5轮迭代修改，每次修改都在2分钟内生成新版本，并支持版本对比和回滚

- **SC-007**: 系统支持导出为至少3种格式（Markdown、PDF、Word），导出成功率达到99%以上

- **SC-008**: 用户在首次使用时的任务完成率达到70%以上，即70%的用户能够成功从需求输入到获得完整PRD

- **SC-009**: 对话上下文能够保持至少50轮对话不丢失，用户刷新页面后可以恢复到之前的状态

- **SC-010**: 后台管理的大模型配置测试连接功能准确率95%以上，能够正确验证baseUrl和apiKey的有效性

- **SC-011**: 限流功能准确率100%，在达到50次/小时（普通用户）或200次/小时（高级用户）上限时准确拦截请求并给出友好提示

- **SC-012**: 并发编辑冲突检测准确率100%，当多设备同时编辑时能在1秒内检测到版本冲突并提示用户

## Clarifications

### Session 2026-02-15

- **Q**: API Key 的安全存储方式是什么？ → **A**: 使用 AES-256 加密存储在数据库中，密钥托管在环境变量，只有后端能解密使用
- **Q**: 对话历史和 PRD 文档的数据保留期限是多久？ → **A**: 保留90天，自动归档到冷存储
- **Q**: 用户在不同浏览器/设备同时编辑同一会话时的并发处理策略是什么？ → **A**: 乐观锁机制，后保存者获胜，显示冲突提示
- **Q**: 大模型 API 调用的限流策略是什么？ → **A**: 分级别限流：普通用户50次/小时，高级用户200次/小时

## Assumptions *(optional)*

- **假设1**: 用户具备基本的产品概念，能够理解目标用户、商业模式、竞品等基础术语

- **假设2**: 大模型API供应商提供稳定的服务，支持标准的REST API调用格式

- **假设3**: 用户上传的文档主要是中文或英文，系统优先支持这两种语言的文档解析

- **假设4**: 系统管理员具备基本的技术背景，能够理解baseUrl、apiKey等配置参数的含义

- **假设5**: 用户对PRD的基本结构有一定了解，能够理解标准PRD的各个章节含义

---

## Dependencies *(optional)*

- **依赖1**: 需要接入Web搜索服务（如SerpAPI、Google Custom Search等）用于竞品分析时的竞品搜索

- **依赖2**: 需要文档解析服务或库（如 mammoth.js、pdf-parse 等）用于解析上传的Word和PDF文档

- **依赖3**: 需要图表渲染库（如Mermaid）用于在界面中渲染流程图和架构图

- **依赖4**: 需要导出功能库（如html2pdf、docx.js等）用于生成PDF和Word格式的PRD文档

---

## Out of Scope *(optional)*

以下功能在本阶段明确排除在范围外：

- 多人协作编辑PRD（实时协同编辑）
- AI自动创建原型设计图（Mockup/Wireframe生成）
- 代码自动生成（根据PRD直接生成可运行的代码）
- 项目管理集成（与Jira、Trello等项目管理工具集成）
- 用户行为分析和埋点自动配置
- 自动部署和CI/CD流程配置
- 多语言PRD生成（除中文和英文外的其他语言）
- 语音输入和语音识别功能

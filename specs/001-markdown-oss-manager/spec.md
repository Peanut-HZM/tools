# Feature Specification: Markdown OSS 文件管理功能

**Feature Branch**: `001-markdown-oss-manager`  
**Created**: 2026-02-11  
**Status**: Draft  
**Input**: User description: "给当前的工具中Markdown编辑器实现一个功能,可以手动上传文件到阿里云的OSS服务器上,然后Markdown的左侧会有一个文件夹,可以展示所有上传到阿里云上的个人的Markdown,可以点击打开对应的Markdown文档.如果阿里云OSS支持创建文件,这里也需要支持创建文件夹,而且要根据当前系统登录的用户对数据进行隔离,确保每个用户都是只能看到自己的文件"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 上传文件到OSS (Priority: P1)

用户可以通过拖拽或点击上传 Markdown 文件到阿里云 OSS，上传后文件会保存在用户专属的云存储空间中，确保数据隔离和安全性。

**Why this priority**: 这是整个功能的基础，没有上传功能就无法使用 OSS 存储。用户需要将本地 Markdown 文件备份到云端或从云端编辑文档。

**Independent Test**: 用户登录后，点击上传按钮或拖拽文件到编辑器区域，文件成功上传到 OSS 并出现在左侧文件列表中。

**Acceptance Scenarios**:

1. **Given** 用户已登录系统，**When** 用户点击上传按钮选择 .md 文件，**Then** 文件成功上传到 OSS 并显示在左侧文件列表中
2. **Given** 用户已登录系统，**When** 用户拖拽 Markdown 文件到编辑器区域，**Then** 文件成功上传并自动打开编辑
3. **Given** 用户尝试上传非 Markdown 文件，**When** 选择 .txt 或 .docx 文件，**Then** 系统提示只支持 Markdown 格式文件
4. **Given** 用户上传同名文件，**When** 文件已存在于 OSS 中，**Then** 系统询问是否覆盖或保留两个版本

---

### User Story 2 - 浏览 OSS 文件列表 (Priority: P1)

在 Markdown 编辑器左侧显示文件树/文件夹视图，展示当前用户上传到阿里云 OSS 的所有 Markdown 文件，支持按文件夹组织。

**Why this priority**: 用户需要知道云端有哪些文件，才能选择要编辑的文件。这是使用云端存储的核心功能。

**Independent Test**: 用户登录后，左侧自动加载并显示该用户的所有 OSS Markdown 文件列表，可以展开/收起文件夹，查看文件层次结构。

**Acceptance Scenarios**:

1. **Given** 用户已登录且有 OSS 文件，**When** 打开 Markdown 编辑器，**Then** 左侧自动加载并显示用户的 OSS 文件树
2. **Given** 用户点击文件夹，**When** 展开文件夹节点，**Then** 显示该文件夹下的所有子文件和子文件夹
3. **Given** 用户文件较多，**When** 列表加载时，**Then** 显示加载状态，加载完成后显示文件数量和最后修改时间
4. **Given** 用户没有 OSS 文件，**When** 打开编辑器，**Then** 左侧显示空状态提示"暂无云端文件，请上传"

---

### User Story 3 - 打开和编辑 OSS 文件 (Priority: P1)

用户可以点击左侧文件列表中的文件，在编辑器中打开并进行编辑。编辑后的内容可以保存回 OSS。

**Why this priority**: 这是用户使用云端存储的主要目的——编辑文档。没有编辑功能，上传和浏览就失去了意义。

**Independent Test**: 用户点击左侧文件列表中的文件，文件内容加载到编辑器中，用户修改后点击保存，文件成功更新到 OSS。

**Acceptance Scenarios**:

1. **Given** 用户看到左侧文件列表，**When** 点击某个 Markdown 文件，**Then** 文件内容加载到右侧编辑器中
2. **Given** 用户正在编辑 OSS 文件，**When** 修改内容后按 Ctrl+S，**Then** 文件成功保存到 OSS 并显示保存成功提示
3. **Given** 用户正在编辑文件且有未保存修改，**When** 尝试关闭页面或切换文件，**Then** 系统提示"有未保存的修改，是否保存？"
4. **Given** 网络不稳定，**When** 保存文件时网络断开，**Then** 系统提示保存失败，并保留编辑内容允许重试

---

### User Story 4 - 创建文件夹管理文件 (Priority: P2)

用户可以在 OSS 中创建文件夹来组织 Markdown 文件，支持在指定文件夹下创建新文件或子文件夹。

**Why this priority**: 当文件数量增多时，文件夹组织能提高工作效率。这是一个增强功能，不是基础功能的必需部分。

**Independent Test**: 用户在左侧文件树中右键点击，选择"新建文件夹"，输入名称后创建成功，可以在该文件夹下创建新文件。

**Acceptance Scenarios**:

1. **Given** 用户在文件树区域，**When** 右键选择"新建文件夹"并输入名称，**Then** 在 OSS 中创建对应前缀的文件夹
2. **Given** 用户在某个文件夹内，**When** 点击"新建文件"，**Then** 新文件创建在当前文件夹路径下
3. **Given** 用户尝试删除文件夹，**When** 文件夹内有文件，**Then** 系统提示"文件夹不为空，是否删除所有内容？"
4. **Given** 用户重命名文件夹，**When** 新名称已存在，**Then** 系统提示"该名称已存在"

---

### User Story 5 - 文件版本历史管理 (Priority: P2)

系统自动保存每次修改的版本历史到 OSS，用户可以查看历史版本列表并回滚到任意历史版本。

**Why this priority**: 版本控制可以防止误操作导致的数据丢失，让用户更放心地编辑文档。这是一个重要的安全网功能。

**Independent Test**: 用户编辑并保存文件多次后，可以打开版本历史面板，查看所有历史版本的时间线和内容摘要，选择任意版本进行回滚。

**Acceptance Scenarios**:

1. **Given** 用户已保存文件多次，**When** 打开版本历史面板，**Then** 显示所有历史版本的列表，包括保存时间和内容摘要
2. **Given** 用户查看版本历史，**When** 点击某个历史版本，**Then** 在新标签页中预览该版本的内容
3. **Given** 用户发现当前版本有误，**When** 选择某个历史版本并点击"回滚"，**Then** 当前文件内容恢复为该版本，并创建一个新的版本记录
4. **Given** 版本历史较多，**When** 列表加载时，**Then** 支持分页或无限滚动，加载时间不超过 2 秒

---

### User Story 6 - 离线编辑与自动同步 (Priority: P2)

当 OSS 服务不可用时（网络断开、OSS 维护等），用户可以继续编辑本地缓存的文件，系统会在服务恢复后自动同步所有修改。

**Why this priority**: 这能显著提升用户体验，确保用户在任何网络环境下都能正常工作。特别适合移动办公或网络不稳定的场景。

**Independent Test**: 用户在有网络时打开并编辑文件，然后断开网络继续编辑并保存，恢复网络后系统自动将离线期间的修改同步到 OSS。

**Acceptance Scenarios**:

1. **Given** 用户正在编辑 OSS 文件，**When** 网络突然断开，**Then** 系统显示离线状态指示器，允许继续编辑
2. **Given** 用户在离线状态下编辑文件，**When** 按 Ctrl+S 保存，**Then** 文件保存到本地 IndexedDB 缓存，并显示"已本地保存，待同步"
3. **Given** 网络已恢复连接，**When** 系统检测到 OSS 服务可用，**Then** 自动将本地缓存的修改同步到 OSS，并显示同步成功提示
4. **Given** 用户在离线状态下创建了新文件，**When** 网络恢复后，**Then** 新文件自动上传到 OSS，并出现在文件列表中

---

### User Story 7 - 用户数据隔离与权限 (Priority: P1)

每个登录用户只能看到和操作自己的 OSS 文件，不同用户之间的数据完全隔离，管理员也无法查看其他用户的私人文件。

**Why this priority**: 数据安全和隐私是核心需求。没有隔离机制，用户不会信任系统存储个人文档。

**Independent Test**: 用户 A 登录后上传文件，用户 B 登录后看不到用户 A 的文件；用户 A 登出后重新登录，文件依然存在。

**Acceptance Scenarios**:

1. **Given** 用户 A 已上传多个文件，**When** 用户 B 登录系统，**Then** 用户 B 的文件列表为空，看不到用户 A 的任何文件
2. **Given** 用户 A 知道用户 B 的文件路径，**When** 尝试通过 API 直接访问，**Then** 系统返回 403 权限错误
3. **Given** 用户未登录，**When** 尝试访问 OSS 相关 API，**Then** 系统返回 401 未授权错误
4. **Given** 用户删除自己的文件，**When** 操作完成，**Then** 只影响该用户的文件，不影响其他用户

---

### Edge Cases

- **空文件名或特殊字符**: 用户上传文件名包含特殊字符（如 / \\ : * ? " < > |）时，系统自动替换为下划线或连字符，确保文件名合法
- **超大文件**: 用户上传超过 10MB 的 Markdown 文件，系统自动启用分块上传机制，支持断点续传
- **并发编辑**: 系统自动保存版本历史到 OSS 的 `versions/{user_id}/...` 路径下，用户可随时回滚到任意历史版本
- **OSS 服务不可用**: 系统允许离线编辑并本地缓存（IndexedDB），OSS 服务恢复后自动同步缓存的修改
- **网络中断**: 上传或保存过程中网络中断时，保留编辑内容并显示重试按钮，支持断点续传
- **文件被删除**: 用户正在编辑的文件被其他会话删除时，保存操作会重新创建该文件，并保留历史版本用于恢复

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持用户通过点击或拖拽方式上传 .md、.markdown、.txt 格式的文件到阿里云 OSS
- **FR-002**: 系统必须在左侧文件树中展示当前登录用户的所有 OSS Markdown 文件，支持文件夹层级结构
- **FR-003**: 用户必须能够通过点击文件列表中的文件，在编辑器中打开并查看文件内容
- **FR-004**: 系统必须支持将编辑后的内容保存回 OSS，保持文件路径不变
- **FR-005**: 系统必须实现用户数据隔离，每个用户只能访问自己的 OSS 文件（通过 user_id 作为前缀路径）
- **FR-006**: 系统必须支持在 OSS 中创建文件夹来组织文件
- **FR-007**: 系统必须支持删除 OSS 中的文件和空文件夹
- **FR-008**: 系统必须支持重命名 OSS 中的文件
- **FR-009**: 系统必须在文件列表中显示文件的基本信息（文件名、大小、最后修改时间）
- **FR-010**: 系统必须在上传、保存、删除操作时显示加载状态和成功/失败提示
- **FR-011**: 系统必须在文件树中通过图标或标签区分本地文件和 OSS 文件
- **FR-012**: 系统必须自动保存文件版本历史到 OSS 的 `versions/{user_id}/...` 路径，支持用户回滚到任意历史版本
- **FR-013**: 系统必须支持分块上传大文件（超过 10MB），支持断点续传
- **FR-014**: 当 OSS 服务不可用时，系统必须允许离线编辑并本地缓存（IndexedDB），服务恢复后自动同步
- **FR-015**: 系统必须提供版本历史查看界面，显示每个版本的保存时间和修改内容摘要

### Key Entities *(include if feature involves data)*

- **OssFile**: 表示 OSS 中的文件对象
  - file_path: 文件在 OSS 中的完整路径（包含 user_id 前缀）
  - filename: 文件名
  - size: 文件大小（字节）
  - last_modified: 最后修改时间
  - content: 文件内容（仅在读取时包含）
  
- **FileTreeNode**: 文件树节点，用于前端展示
  - name: 节点名称（文件名或文件夹名）
  - path: 节点路径
  - type: 'file' | 'directory'
  - children: 子节点列表（仅文件夹类型）
  - isExpanded: 是否展开（前端状态）

- **UserContext**: 当前用户上下文
  - user_id: 用户唯一标识
  - auth_token: 认证令牌

- **FileVersion**: 文件版本历史对象
  - version_id: 版本唯一标识（时间戳或 UUID）
  - file_path: 原文件路径
  - version_path: 版本在 OSS 中的存储路径
  - created_at: 版本创建时间
  - size: 版本大小
  - content_preview: 内容摘要（前 200 字符）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户可以在 10 秒内完成文件上传到 OSS 的操作（包括分块上传大文件）
- **SC-002**: 文件列表加载时间不超过 2 秒（在 100 个文件以内）
- **SC-003**: 95% 的文件保存操作在 3 秒内完成，包括版本历史的自动保存
- **SC-004**: 用户可以成功管理（上传、编辑、删除）云端文件，操作成功率达到 99%
- **SC-005**: 不同用户之间的文件数据完全隔离，用户 A 无法看到或操作用户 B 的文件
- **SC-006**: 用户数据隔离机制通过安全测试，确保无法通过路径遍历或其他方式绕过
- **SC-007**: 系统支持同时管理本地文件和 OSS 文件，用户可以通过视觉区分两种文件类型
- **SC-008**: 文件上传和保存操作有清晰的错误提示，用户能够理解问题原因
- **SC-009**: 系统保留至少 30 天的文件版本历史，用户可在 5 秒内回滚到任意历史版本
- **SC-010**: 在 OSS 服务不可用时，用户仍可继续编辑本地缓存文件，服务恢复后 10 秒内完成同步

## Clarifications

### Session 2026-02-11

- **Q**: 本地文件和 OSS 文件在文件树中如何展示？ → **A**: 在同一个文件树中混合显示，但有视觉区分（图标或标签）
- **Q**: 并发编辑冲突如何处理？ → **A**: 自动保存版本历史，允许回滚到任意版本
- **Q**: 超出 10MB 限制的文件如何处理？ → **A**: 分块上传大文件（支持断点续传）
- **Q**: OSS 服务不可用时的降级策略？ → **A**: 允许离线编辑并本地缓存，OSS 恢复后自动同步
- **Q**: 版本历史存储位置？ → **A**: 存储在 OSS 的独立前缀下（如 `versions/{user_id}/...`）

## Assumptions

- 用户已登录系统并获得有效的 JWT 认证令牌
- 阿里云 OSS 服务已正确配置且可用
- 用户浏览器支持现代的 JavaScript 和 CSS 特性
- 网络连接稳定（对于大文件上传，应有断点续传或重试机制）
- 单个 Markdown 文件大小不超过 10MB
- 用户文件数量在合理范围内（少于 1000 个文件），不需要复杂的分页和搜索优化
